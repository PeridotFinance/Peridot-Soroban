## Proactive maintenance remains conditional arithmetic

For the **latest seven shared non-native-marker code entries**, reuse the pinned formula from [cost-study.py](cost-study.py): rent rate 1,000 stroops/KB, persistent denominator 1,215, code discount 3, and TTL metadata writes of 1,250 stroops per entry plus 437 stroops/KB for 48 bytes per entry. Apply the extension only to unchanged code that is already live; do not charge its entire restored lifetime again. These code entries still include compiled controlled-state fixtures and are not a reviewed production registry.

| Additional live ledgers | Code payload rent + TTL-write component | Complete maintenance operation fee |
|---:|---:|---|
| 17,280 | **4.4817399 XLM** | Unmeasured |
| 518,400 | **134.4263898 XLM** | Unmeasured |
| 2,073,600 | **537.7028897 XLM** | Unmeasured |

At an assumed five-second ledger cadence, those ledger counts correspond to 1, 30 and 120 days. They are not measured elapsed durations or an adopted schedule. The preserved older liquidation-code estimates, 4.3987501 / 131.9366953 / 527.7441119 XLM, refer to a different code set; the difference is not a measured optimization result.

The calculation is reproducible from each latest `shared_code` key's `rent_size_bytes` in `shared-results.json`. For extension `L`, sum `ceil(ceil(size * 1000 * L / (1024 * 1215)) / 3)` over those seven keys, then add `7 * 1250 + ceil(48 * 7 * 437 / 1024)` stroops. This excludes whole-operation overhead and every instance/data extension. Do not treat 134.4263898 XLM as a complete monthly operating allowance.

Maintenance can reduce emergency archive discovery, repeated parsing and confirmation delay. It does not make long-lived storage free: each additional byte-ledger still costs rent, and frequent extensions repeat transaction overhead. Before selecting a cadence, inventory the actual code/instance/data dependencies and TTLs, measure complete unsigned extension operations and supported account costs, and compare the resulting expense with observed usage and cold-incident frequency. Existing financial calls may already extend TTLs; a maintenance model must not bill those same byte-ledgers twice.

## Is this worth pursuing?

Yes, as a bounded qualification experiment: the latest shared sequence demonstrates that 54 common dependencies need not be restored independently eight times, while complete historical reward ownership and atomic repayment/seizure are retained for the tested route. The initial economic priority is to qualify accountable shared TTL maintenance and supported real-account execution, not to allocate a fully cold budget to every position or consume the proposed resource headroom.

Affordability remains conditional. Compare actual collected strategy income with measured recurring maintenance, financial calls, failed included transactions, keeper compensation and funded losses at a stated workload. Count cold incidents only using measured joint recovery sequences, and count each fee once. No yield, XLM/USD rate, incident frequency, safe CL size or income sufficiency is established here. The large cold/code-rent component could dominate a small strategy even when a warm root looks inexpensive.

Future income, unclaimed rewards and quarantine are not current funding. The separate 50% eligible-income reserve-replenishment scenario must use its defined eligible-income basis and cannot count the same collected unit simultaneously as operating cash and reserve replenishment. No reserve seed/cap or shared policy is revised by this document. [shared-results.md](shared-results.md) preserves the exact conservation result; physical quarantine zero during this continuous-outage cost fixture does not prove that unobserved rewards are unowed.
